## Current performance

| Measure | Interpreter | Default JIT | JIT with compiled calls | Node 24.19.0 (V8) |
| --- | ---: | ---: | ---: | ---: |
| Octane throughput score, higher is better | 5,245 | 5,646 | 5,616 | 55,783 |
| Verified 64-item HTTP orders/s | 4,247 | 4,347 | 2,980 | 9,440 |
| Server CPU, µs/order | 227.30 | 221.98 | 320.44 | 55.65 |

V8 scores **9.88×** the default JIT on Octane. The JIT gains 7.65% over the interpreter, but Crypto accounts for most of that gain. The other 14 workloads average **1.34%** above the interpreter on the geometric mean. DeltaBlue is the widest gap to V8 at 54.76×. The HTTP benchmark measures the full embedded service on one persistent connection, with byte-verified replies. [Per-workload Octane results](jit-scorecard-results/2026-11-19-http-calls/octane.md) · [HTTP timings and controls](jit-scorecard-results/2026-11-19-http-calls/README.md)

**Keep the lexical-read change.** At `aa564dec`, a statically known lexical slot compiles to a direct x86 load. On the HTTP fixture this cut scope-helper calls per order from 32 to 2 by default and from 274 to 2 with compiled calls enabled. Against `62790abf`, default server CPU fell 3.0% in six paired fresh-process rounds and 2.2% in four warmed process pairs. The interpreter-only controls also moved, so the share of that gain attributable to the loads remains uncertain. Three other experiments shortened linked-call entry, packed saved values, or specialized field definitions. Each improved a local counter. None produced a repeatable service CPU win. [Experiments and retained branches](jit-scorecard-results/2026-11-19-http-calls/README.md)

## Resume at the nested HTTP call

Follow `parserOnBody` → `Readable.prototype.push` → `readableAddChunkPushByteMode`. On `62790abf` with compiled calls enabled, all **128 of 128** measured `stream.push(b)` calls at parser bytecode PC 54 entered compiled `push`. Every call then suspended at PC 48 inside `push`. The VM resumed the parser normally after saving and restoring six live values. In the 64-order window that also recorded the inner target, the byte-mode routine had no installed machine code on every call. An independent trace saw that routine compile, deoptimize eight times in eight entries, then unlink. It recorded PC 194 (`get_arg_length8`) and PC 8 (`get_array_el3`), without a count for each site. These traces establish the route. The CPU recoverable at this edge is still unknown. ## Build and verification

Use the pinned Silk dev.74 toolchain and Clang 22.1.8. Run these commands from the repository root.

```sh
silk test --manifest-path modules/jit/silk.toml
silk build --release --manifest-path modules/engine/silk.toml
silk build --release --manifest-path modules/jit/shell/silk.toml
silk build --release --manifest-path modules/jit/embed-smoke/silk.toml
```

To repeat the HTTP comparisons in this workspace, set `BASE_HOST` to the baseline release embed executable and `CANDIDATE_HOST` to the new one. Use fresh output filenames and Node 24.19.0 on `PATH`. The original fresh-process driver pins the server to CPU 0 and the client to CPU 4.

```sh
results=docs/jit/jit-scorecard-results/2026-11-19-http-calls
python3 "$results/compare.py" --repo . --host base "$BASE_HOST" \
  --host candidate "$CANDIDATE_HOST" --node "$(command -v node)" --out /tmp/silk-http-fresh.json
python3 "$results/paired.py" --repo . --base "$BASE_HOST" \
  --candidate "$CANDIDATE_HOST" --out /tmp/silk-http-warmed.json
```

The retained change passed 93 native JIT tests, 45 fixed-work Octane correctness runs, and 300 generated programs across 13 configurations. All ten JIT configurations compiled and exercised deoptimization on every generated program. The official Octane timing run completed 180 fresh processes. The linked records include exact binary hashes, seed ranges, modes and suite commands.
