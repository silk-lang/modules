# SilkJS JIT: strategy plan

20 November 2026 · for Julia · Markdown copy of the doc [SilkJS JIT: strategy plan](https://claude.ai/artifact/TsiVFpheNgpzfrLxVwcCcP), which also has the tier diagram. Revised the same day against `work/x86-milestone` at `4cfc05ae`.

## Verdict

The compiler is not what is slow. The boundary around it is. Code that stays inside compiled code already runs 1x to 4x behind V8 on the kernels, yet Octane gains 7.65% and the HTTP service 2%, because real programs leave compiled code all the time and every way out is expensive or permanent.

The plan is to stop widening the fast path and fix the boundary, then return to optimization on one benchmark at a time:

1. **Add a baseline tier under the SSA compiler.** It compiles every function, never refuses and never deoptimizes, and it runs on the interpreter's own frame. This is what puts the full hot path in machine code, which is where you saw gains appear.
2. **Make every slow path a call, not an exit.** A cache miss, a generic operation or a call into the interpreter stays inside compiled code and costs tens of instructions, not a round trip through the VM.
3. **Collect feedback in baseline code.** It is always on, costs the interpreter nothing, and replaces the 500-instruction recording window.
4. **Keep the SSA compiler as the second tier.** It speculates only on mature feedback, exits into baseline code, and is never unlinked for good.
5. **Use what a server runtime has and a browser does not.** Compile Node's internal JS at build time, persist profiles and code per deployed module, compile on a spare core, and offer an opt-in closed world.
6. **Work one vertical at a time:** Richards, then DeltaBlue, then the HTTP order service. Steer by share of time in machine code and exits per call, and judge by the benchmark's own score.

The 1.3x of V8 on Octane target is not reachable in one step from 9.88x. I propose three gates before it: Richards at 5x the interpreter, the HTTP service at 145 µs per order, and Octane at 3x the interpreter. The last third of the Octane gap needs allocation and collector work that this plan parks. On the HTTP service the compiler can reach about 55% of the CPU. The rest is kernel, allocation, JSON and native runtime code, and it needs its own lane to get near Node.

**Checked against `work/x86-milestone` at `4cfc05ae` on 20 November.** The first version of this plan was written from the 18 November state. The 19 November measurements support the diagnosis and add the CPU evidence it lacked. They changed three things here. The HTTP gate moved from 120 to 145 µs because only part of a request is JS execution. Step 0 now starts by moving the branch onto main. The HTTP vertical targets the runtime's own request path, because 60 extra line items add only 23 µs to a 206 µs request.

## Diagnosis

Where code compiles and stays compiled, it is fast. Where a real program runs, it is not, and the measurements say why.

| Evidence | Number | What it says |
| --- | --- | --- |
| Loop kernels, 18 Nov gated head | 1.6x to 3.9x behind V8 | Code generation for arithmetic is sound |
| Calls and method kernels, ungated preview | 2.2x to 2.3x behind V8, 18 instructions per call against 335 interpreted | Calls can be cheap when both sides are compiled |
| Richards with compiled calls | All 13 reported hot functions compiled, 59.8% of instructions in compiled code, score 1.28x the interpreter on 19 Nov (V8 is 26x) | Even a fully compiled path gains little: the glue between functions eats it |
| DeltaBlue with compiled calls | 55 compiled, 234 deopts, 29 unlinked on 18 Nov. Score 1,940 against 1,935 interpreted on 19 Nov (V8 is 55x) | Guesses fail and the functions fall back for good |
| TypeScript with compiled calls | 302 compiled, 2,003 deopts, 246 unlinked | Same, at scale |
| Mandreel, Box2D with compiled calls | 33.5% and 15.4% of instructions are the compiler | Compiling on the main thread is charged to the benchmark |
| HTTP order service | 227 µs interpreted, 222 default JIT, 320 compiled calls, Node 55.65 | Turning calls on makes the server slower |
| HTTP with compiled calls, CPU sampled on 19 Nov | Per order: interpreter loop -18 µs, generated code +43, VM call handling +21, JIT helpers +13, kernel +11, whole process +104 | Taking 18 µs out of the interpreter added 122 µs elsewhere. The boundary costs more than the dispatch it removes |
| Generated code on that service | 35% of its samples are entry, resume and call sequences. After 4,800 warm orders the compiler hook still runs 62,177 instructions per order, 6.7% of the total | The boundary is paid inside compiled code too, and exits keep code churning in steady state |
| HTTP parser path | 128 of 128 `push` calls suspended at one inner call; the inner routine deopted 8 times in 8 entries, then was unlinked | One uncompiled callee breaks the chain for its callers |
| HTTP by order size, 19 Nov | 4 items: 206 µs, Node 46. 64 items: 229 µs, Node 54 | About 90% of the CPU is per-request work that does not grow with the order: parser callbacks, streams, emitter, ticks and response code in the runtime's own JS, plus kernel and native work |
| HTTP default JIT, CPU split, 19 Nov | Of 237 µs sampled: interpreter loop 84, calls and property operations in the VM 46, kernel 28, allocation and collection 19, JSON 13, other native code 47 | The compiler can reach about 55% of a request. The other 107 µs is twice Node's whole request |
| Express request (13 Nov) | 41.6% of instructions in the dispatch loop, the rest in helpers; a generic builtin call costs about 1,000 | A JIT alone cannot close the server gap; builtin calls matter as much |

Five causes sit behind these numbers, all at the boundary.

1. **Two frame worlds.** Compiled code keeps its own state, so crossing means copying: call blocks, an activation side stack, exit tables, published frames. `compiled-entry.md` says it directly: "a call is an exit, not a native call", because engine functions are generic over hooks and cannot be named from machine code.
2. **Guess, exit, unlink.** A failed guard returns to the interpreter. Eight failures unlink the function and two recompiles is the limit. `compile-cost.md` already names the fix: "those sites need a slow path in compiled code instead of an exit".
3. **Thin feedback.** Types are recorded in the observed loop, at about 170 instructions per bytecode instruction, for 500 instructions plus 2 per bytecode byte. Always-on recording was ruled out by the 0.5% interpreter budget. JSC runs a function about 1,000 times in a profiling tier before its first optimizing compile.
4. **Server code is not covered.** Async functions, generators and module bodies never run compiled, and loops compiled for OSR refuse calls. A Node request path is mostly async functions.
5. **Compilation runs on the main thread.**

Your observation follows from causes 1 and 2. When one function on a path is refused or unlinked, each neighbour's call to it becomes an exit that costs more than the interpreter's own call. A local improvement then shows on its counter and vanishes in the total, which is how three of the four 19 November trials ended.

The pieces that work are worth keeping: the encoder and code memory, the SSA form with ownership, unboxed loops, inlining, relocatable code, the differential harness and the scorecard.

## Prior art

Every production engine that speculates puts a cheap, non-speculating compiled tier underneath, and the server VMs closest to SilkJS steer by real workloads. We built the speculating tier first.

| System | What it does | Measured | Lesson for SilkJS |
| --- | --- | --- | --- |
| [V8 Sparkplug](https://v8.dev/blog/sparkplug) | One pass from bytecode, no IR, same frame as the interpreter, mostly calls the interpreter's own builtins | Speedometer +5 to 10%; over the interpreter alone, JetStream +45% and Speedometer +41% (figures from the Maglev post) | A shared frame makes OSR, exceptions and stack walks free. V8 added this tier after years of interpreter plus optimizer |
| [V8 Maglev](https://v8.dev/blog/maglev) | SSA on a CFG, built in one pass from bytecode and feedback | Compiles about 10x slower than Sparkplug and 10x faster than TurboFan | Our SSA compiler is this design point. Cheap compiles make a wrong guess tolerable: deopt and recompile |
| [JavaScriptCore](https://webkit.org/blog/10308/speculation-in-javascriptcore/) | Four tiers. Lower tiers profile, the DFG exits to Baseline | Per bytecode: LLInt 3.97 ns, Baseline 1.71, DFG 0.349, FTL 0.225 | Baseline is 2x, and the optimizer is 5x on top of it. Speculate only when profiles agree; otherwise branch to a slow path |
| [HHVM](https://blog.acolyer.org/2018/08/08/hhvm-jit-a-profile-guided-region-based-compiler-for-php-and-hack/) | Reference-counted server VM. | [YJIT](https://railsatscale.com/2023-09-18-ruby-3-3-s-yjit-runs-shopify-s-production-code-15-faster/) | Ruby JIT built for Rails servers | +15% on Shopify production; about 85% of instructions run in JIT code | Steer by [share in JIT and exits per instruction](https://railsatscale.com/2023-06-05-monitoring-yjit-in-production). | [CPython JIT](https://fidget-spinner.github.io/posts/jit-reflections.html) | Copy-and-patch over a specializing, reference-counted interpreter | 3.13: slower to equal. 3.14: often slower than the interpreter | Removing dispatch from a good interpreter buys almost nothing alone. The gains are in calls, types and count removal |
| [Deegen](https://arxiv.org/abs/2411.11469) | Baseline JIT generated from the interpreter's semantics, same frame, inline caches for properties and calls | Baseline 360% faster than PUC Lua where its interpreter is 179% faster, so about 1.65x its own interpreter; 33% behind LuaJIT's optimizer | A baseline with good call and property caches over a fast interpreter is worth roughly 1.5x to 2x |

| [HotSpot Leyden](https://openjdk.org/jeps/483) | AOT cache from a training run: linked classes, then [profiles](https://openjdk.org/jeps/515), then [code](https://openjdk.org/jeps/8335368) (draft) | Spring PetClinic start 4.486 s to 2.604 s; profiles cut a small program's warm-up 19% | Same order for us: image, profiles, code. A mismatched cache is ignored, never trusted |
| [V8 embedded builtins](https://v8.dev/blog/embedded-builtins) | Builtin code compiled at build time into the binary, reaching the heap through a roots register | Median V8 heap down 19% | The model for shipping Node's internal JS as compiled code |

Two cautions from the same sources. HHVM discards Hack type hints at run time because the type system is unsound, so TypeScript annotations can seed a guess but never remove a check. And the YJIT team compares each release against the previous JIT as well as the interpreter, because a slower interpreter flatters the JIT.

## What a Node-only runtime can do that V8 cannot

V8 has to assume a browser: unknown code, short sessions, untrusted pages. SilkJS knows its own runtime JS at build time, knows the deployed modules at load time, and runs for hours on a machine with spare cores.

| We have | It allows | Step |
| --- | --- | --- |
| Node's internal JS is ours and fixed at build time. The measured HTTP path (`parserOnBody`, `Readable.prototype.push`, `readableAddChunkPushByteMode`) is entirely internal code | Compile it at build time from a training profile and ship it in the heap image. Node re-JITs the same code in every process | 7 |
| The loader knows each deployed module by content | Persist feedback and compiled code per module. The second start, each worker and each replica begin warm | 6, 8 |
| Long-lived processes on multi-core hosts | Compile on a background thread and spend more per function, with thresholds tuned for throughput, not first paint | 5 |
| A deploy step exists | A training run (tests or replayed requests) writes the profile, as Leyden and Jump-Start do. `--build-snapshot` already carries a warmed heap | 6 |
| Trusted code and an owner who can opt in | A closed-world flag: frozen builtins, sealed module graph, no `eval`. Builtins and imports become constants. Off by default, since polyfills and APM agents patch prototypes | 9 |
| Reference counting and a heap that never moves | No stack maps and no write barriers, so machine code can call the runtime like C. The current design treats calls as the hard part; this memory model makes them the easy part | 1, 2 |
| Request-shaped work | Steer by CPU per verified order, not by a loop kernel | all |

Without the closed-world flag, the same facts are still usable as guarded assumptions. The engine already has a shape epoch for prototype validity, so "nobody replaced `Readable.prototype.push`" is one epoch check, with a recompile when it breaks.

## Strategy: three tiers on one frame

Interpreter, baseline and optimizer all run on the interpreter's frame, so a function can change tier at any bytecode boundary and no transition copies state.

```
            warm (call and loop counters)        feedback settled
Interpreter ------------------------------> Baseline ------------------------> Optimizer
     ^                                       |  ^                                 |
     |      (baseline code never leaves)     |  |   a guess fails: write live     |
     +---------------------------------------+  +---  values to the frame, go on -+
                                                      in baseline at that bytecode

All three run on the interpreter's frame. Every tier reaches the engine by calling it.
```

Read it left to right: code moves up a tier when it is warm and when its feedback settles, and a wrong guess drops one tier, not to the interpreter. Every tier reaches the engine by calling it.

| Tier | Compiles | Guesses | When a check fails | Feedback |
| --- | --- | --- | --- | --- |
| Interpreter | nothing | site caches, as today | its own slow path | none, as today |
| Baseline (new) | every function that gets warm, in one pass from bytecode | nothing beyond inline caches | calls the interpreter's general step for that instruction, on the same frame | writes shapes, call targets and operand types to a per-function vector |
| Optimizer (today's SSA compiler) | hot functions whose feedback has settled, on a background thread | types, shapes, call targets, inlining | writes live values back to the frame and continues in baseline code at that bytecode | reads the vector |

### The baseline tier

- **Frame.** Locals and operands stay in their 16-byte slots in the call-frame region. Registers hold temporaries inside one instruction. There is no exit state, call block or activation stack.
- **Opcodes.** About 40 get inline code: locals, constants, integer arithmetic, compare and branch, cached field reads and writes, calls, return. Every other opcode is one call to the interpreter's general step, which stream N already isolated as `genericStep`. Coverage is complete on day one, and later work makes opcodes faster, not possible.
- **Calls.** Push the callee's frame as the interpreter does, then make a machine call to its code. A callee without code runs through a trampoline into the dispatch loop on that frame. A native is called directly. Errors come back as a status that the caller tests, so nothing unwinds through machine frames.
- **Await and yield.** Store the bytecode offset in the frame and return. Resume through a table from offset to address. This is what lets async functions and generators compile.
- **Engine access.** The JIT host knows its concrete hooks and allocator, so it can define each engine entry as an `extern "C"` function. O1's unfinished work found this route around Silk's SEM0188. A compiler change that exports a monomorphized instance would be cleaner.
- **Caches as data.** Inline caches live in a table beside the code, never in patched instructions. Code stays pure and relocatable, so ahead-of-time compilation is the same compiler run earlier.

### The optimizer after the change

- It is entered from baseline counters once a function's feedback has stopped changing.
- A site with mixed feedback gets a branch to a slow-path call, not a guard. Bun's AOT, HHVM and JSC all do this.
- An exit costs tens of instructions: write back, jump into baseline code.
- No function is refused for good. Repeated exits at a site trigger a recompile with that site made generic, with backoff. JSC's defaults, from memory, are 100 exits and a doubling per recompile, against 8 and a two-recompile limit here.

### What this retires

Call exits and call blocks, the activation side stack and hand-off parking, generic instruction exits, the refused-callee deopt rule, unlinking after eight deopts, recording in the observed loop, and `--jit-calls` as a separate mode. The ten JIT configurations in the differential become three: baseline, optimizer, optimizer under stress.

The interpreter-only product is untouched. Linking baseline code can reuse the frame-cells sentinel, which already costs the interpreter 0.02%, and a feedback vector is allocated only when a function gets baseline code.

### The fallback

If the spike in step 2 fails its gate, fix the SSA compiler in place: slow-path calls through the same trampolines and no permanent unlinking. That keeps the second frame world and still cannot run async functions, which is why it is second choice.

Every payoff figure is my estimate, not a measurement. The HTTP figures take the JS-execution share of the 19 November CPU split, about 122 of 222 µs, and assume the baseline tier runs it 1.45x faster and the optimizer 2.7x faster.

Parked: a bump allocator and a generational collector. Splay and EarleyBoyer are bound by memory management, so the last third of the gap to V8 waits on that decision.

**Outside the compiler: the other 100 µs of an HTTP order.** If JS execution cost nothing, the service would still take about 100 µs per order, 1.8x Node. Kernel time alone is 28 µs against 54 for Node's whole request, allocation and collection take 19, and JSON takes 13. A runtime lane on those three can run beside steps 1 to 3 without touching the JIT. The 1.3x server target needs it as much as it needs the compiler.

### How to run the work

- **One vertical at a time, on one integration branch.** At most three streams: the engine seam, the baseline emitter, and measurement. The eight-stream layout produced merges faster than results.
- **A path checklist per vertical.** List every function on the hot path with its tier and its departures per call. Enabling work merges when the checklist moves, even if the score does not. The score is judged at the vertical's gate.
- **Keep the gate chain.** JIT tests, differential 3,000, interpreter-only instructions within 0.5%, the native suite, and the paired timing protocol.
- **From the handoff's next experiment, keep only the trace.** Recording the receiver, key and failing guard at the two deopt sites in `readableAddChunkPushByteMode` belongs in step 0, because it shows what feedback that routine needs. The per-site fix and its timing run are what step 2 gives every site at once.

## What to stop, and what could prove this wrong

Stop until step 3 is through its gate:

- New speculative fast paths, new exit kinds, and new rules for when a caller leaves for a callee.
- Trials judged on a local counter. Linked-call entry, packed saved values and specialized field definitions each improved theirs and moved nothing.
- Unlinking as a policy, and recording in the observed loop.
- Octane geomean as the weekly score. It is a regression check until step 10.

| Risk | Why it is real | What limits it |
| --- | --- | --- |
| The baseline tier gains too little | CPython's JIT over a specializing interpreter was no faster for two releases, and SilkJS's interpreter is already fused and cached | The step 2 spike on Richards costs days. Its gain comes from calls (157 to 335 instructions interpreted, 18 measured compiled), not from dispatch. Below 1.3x, take the fallback |
| Machine code cannot call the engine cheaply | Engine functions are generic over hooks and allocator effect | Per-host trampolines, or a Silk change. Compiler work is in scope |
| Baseline code is large | 16-byte slots and a helper call per rare opcode | Compile after a warm-up count, and measure code bytes per bytecode byte in step 2 |
| The interpreter-only budget | Baseline needs a link check and a feedback vector | Reuse the frame-cells sentinel and allocate vectors at compile time. Hold the 0.5% gate |
| Persisted code goes stale | Code depends on bytecode, engine build and value layout | Key on all three. A mismatch means the cache is ignored |
| 1.3x of V8 on Octane | It needs allocation and collector changes that are parked here | Gates at 5x on Richards, 145 µs per order and 3x on Octane come first |

The plan is wrong if step 0 shows that compiled Richards code is slow for a reason other than calls and transitions, or if the step 2 spike lands under 1.3x. Either result is known within the first two weeks.
